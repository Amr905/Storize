### Governor discipline (item 1)
- All sends: `DirectExtractor._governed` is the only place the extractor sends; it wraps `_http.send` in `governor.run(cost: api)`. The probe uses the same form. The only ungoverned send is `IgProbe.checkCdn` (by design, ADR-9).
- Nothing is nested or unawaited inside `call`: the closure only sends and classifies. The transports `await` each `call(...)` one after another, outside any other `call`. Tested via the 2-call `resolveUser`/`latestPostTime` flows, `maxInFlight == 1` and no timers/requests after completion. The T-012 N1 rule holds. Note for T-014: a `PageTokenProvider`/`DocIdResolver` that loads a page runs between governed calls, not inside one; it must take its own governed `pageLoad` cost and must not be called from within a `call` closure.
- Cost is `api` for every call, including the second call of `resolveUser` over GraphQL and the extra profile call of `timeline` without a username hint (so `fetchNewPosts` right after `refreshUser` costs 1, after nothing costs 2).
- 429 is reported as `RateLimited(Retry-After)`, returned as `Err(RateLimited)` from the closure, which the governor recognises (`_rateLimitOf`); a repeat is not double reported because `GovernorPaused.toFailure()` is returned as is.
- A `Retry-After` in HTTP-date form is read as null (QA-F6), so the governor uses its 15 min default (fail-safe, not a ban risk). A huge value (99999999999 s) is passed through and the governor caps it at 24 h; a negative value is null.
- CDN check host: **no allow-list** (QA-F10).
- Probe call count: one `run()` is 5; two `run()` calls are 10 (only the governor limits it).

### Watermark and `latestPostTime` (item 3, with RunCheck semantics)
TECH_SPEC (RunCheck rule near line 385): `posts_watermark_at` is the `taken_at` of the newest post when the account was added (FR-63); a post is new when `posted_at > watermark` and
`(target, POST, remote_id)` is not stored; after each successful run the watermark moves to the newest `posted_at` seen. The extractor is consistent with it:
- Equal timestamp: excluded (exclusive, tested). Older pinned post: ignored. New pinned post: returned once, newest first, even when the page lists it twice.
- Add then check: `latestPostTime` as the watermark gives an empty `fetchNewPosts` also when the newest post is pinned (tested). Excluding pinned posts from `latestPostTime` would make the existing pinned post download as new on the first run (tested as the counter-example). **Recommendation: keep "max over all posts, pinned included".** It never produces a duplicate or a miss that the exclusive rule does not already produce; the RunCheck dedup on `(target, POST, remote_id)` is the second safety net.
- Known, accepted gaps (not defects, document in RunCheck): (a) a post that shares the exact second of the watermark post is missed (rare); (b) `taken_at` can be earlier than the time Instagram made the post visible (a post made earlier, published later), so it can fall under the watermark and be missed; the page holds only 12 posts so a burst of more than 12 posts between two checks is also missed (ADR-0010 accepted this). RunCheck should move the watermark to `max(taken_at)` of **all** returned entries, not only of the mapped new ones, and `fetchNewPosts` does not expose that value: `latestPostTime` costs another call. If T-017 wants "advance the watermark without an extra call", T-015 should add a combined method (new posts plus newest time) rather than call both.
- `fetchNewPosts` with a malformed old edge fails (QA-F3), which would block the run forever for that target: priority for T-015.

### Opinion on the open design points (mapping to the developer's list is yours)
1. **REST transport (IG-1..5) is an unverified hypothesis.** Keep it, but wire GraphQL as the default in T-015 and select REST only where the probe printed `restProven=true` on the phone. `RestTransport` has no fixture of a real reply; treat any "REST works" claim as unproven until the probe runs.
2. **DASH-only handling.** Dropping the slide and recording `unsupported_stream` is right. T-018 must create the item as `FAILED(unsupported_stream)` (including the all-DASH post with `slides: []`) so it is visible in the UI and not silently skipped.
3. **Owner id from non-collab posts.** Acceptable only with a username check and a majority vote (QA-F2).
4. **`latestPostTime` includes pinned posts.** Keep (see above).
5. **Two calls for `userByUsername` and for an uncached `timeline`.** Acceptable for add flow; fix the per-round cost (QA-F13) before T-017.
6. **`DocIdResolver` and `PageTokenProvider` returning `SchemaChanged` when missing.** Correct and safe: nothing is sent. Page mode (T-014) must supply them. Whether a plain client can get `fb_dtsg`/`lsd` without a page load is unknown (documented in INSTAGRAM_EXTRACTION.md); this is the real feasibility risk of direct mode.
7. **Live items and the `broadcast_id`/`is_live` heuristic.** Synthetic and unverified; the real capture has no live item. Confirm on the phone with a live story.
8. **Probe on the user's phone.** Run it only with the Lead's go-ahead: fix QA-F9 and QA-F10 first (cheap), because the probe uses the real session.
