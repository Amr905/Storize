# T-019a QA review: MediaCache.deleteThumbnail + orphan-thumbnail sweep

Branch `t-019a-thumbnails`, developer HEAD ce191cf. QA: independent verification.

## Verdict: PASS, with one MAJOR carry-forward for T-021 (not a defect of this diff)

The code does what was delivered and is safe against every filesystem edge case I tried. But the new sweep makes the
`keepIds` argument of `cleanupOrphans` dangerous for the T-021 startup call (F1). It must be fixed in the port doc
(or the API) before T-021 starts, which is why I list it as major. It does not block merging T-019a, because nothing
calls `cleanupOrphans` yet.

## Findings

### F1 (major, carry-forward to T-021 / Lead decision): one `keepIds` set for two different live-sets
- Part files are keyed by `mediaFileId`, thumbnails also by `mediaFileId`, so they share one id space. But their
  "live" sets differ. A part file is live only while a download is pending (it is discarded after `GalleryStore.save`).
  A thumbnail is live for every media row that has one, including all downloaded content.
- The port doc says only "whose media file ID is not in keepIds". The carry-forward in `implementation-status.md`
  says "T-021: call `MediaCache.cleanupOrphans()` at start" and T-010's review describes `keepIds` in part-file terms
  (pending downloads). A T-021 author who follows that passes the pending ids, and the new sweep then deletes the
  thumbnail of every downloaded item. Proven by the test `BLOCKER probe` in `qa_t019a_test.dart` (downloaded media 1
  loses its thumbnail when `keepIds = {2}`).
- The reverse also holds: passing every live media id keeps stale parts of already-downloaded media (small leak).
- Recommendation (pick one): (a) separate methods, `cleanupOrphans(Set<int> pendingIds)` for parts and
  `cleanupOrphanThumbnails(Set<int> liveMediaIds)`, or (b) one method with two named parameters. At minimum (c)
  rewrite the port doc and the T-021 task so the caller must pass the ids of ALL media_file rows, and add a T-021 test
  that a downloaded item's thumbnail survives startup. (a) or (b) is safer because the type system cannot express (c).

### F2 (info): negative ids
`-5.webp` round-trips, so it is treated as id -5 and swept unless kept. Ids are positive autoincrement, so harmless.

### F3 (info): thumbs directory that is a symlink
The thumbs directory itself, if a symlink, is followed (the entries inside are listed). It sits in the app-private
support dir, so it is trusted. Only exact `<int>.webp` regular files inside it can be removed; other files survive.
Tested, no change requested.
