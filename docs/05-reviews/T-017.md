## Coverage of the top risks
1. Watermark: unchanged after a failed call and after a partial insert failure (rerun gives no duplicates). An old pinned post does not hide new ones. The mark is the max of all returned posts, including filtered reels. Equal timestamps are both stored. The mark never moves backwards.
2. Stories: rerun is idempotent. A story missing from a later response is kept (BR-4). With 45 targets and batch 2 failing, batches 1 and 3 are stamped and batch 2 is not.
3. BR-7: needsRelogin, restricted and loggedOut, for both scopes: zero platform calls, and `check_run` is finished.
4. Isolation: a platform throw for one target, or a content insert exception, does not stop the others. A throwing settings repo still leaves a finished `check_run` (FAILED).
5. Fairness: 7 posts targets with a budget of 3 per run, all checked in 3 runs. 45 story targets with one batch per run, all covered in 3 runs.
6. EC-3..EC-6: `NetworkFailure` changes no status and writes no event. NotVisible and NotFound change only their own target.
7. FR-67: a reels-only target stores reels only. A paused target is skipped.

## Findings
- F1 (Low, design note, not a bug under the current spec): the watermark is a strict `isAfter`. A post that appears later with exactly the same timestamp as the stored mark (same-second upload after a check) is never fetched as new. The tie is only safe within one response. Consider `!isBefore` plus dedup by the unique key, which the insert path already has.
- F2 (Low): a target that always returns SchemaChanged and sits first in the round-robin order, three in a row, ends the run (`_maxSchemaFailures`). Because failed targets are never stamped, they stay at the front, and later targets can starve while the schema stays broken. This is acceptable because it is a platform-wide failure. It is not covered by a test.
- F3 (Info): in a stories batch, a platform throw or a Network error fails the whole batch of 20. There is no per-target isolation inside a batch, which matches the design.
