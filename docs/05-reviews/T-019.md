## Findings

### F1 (major, decision needed): retention age uses `postedAt`
- Spec: FR-54 "auto-delete after N days"; UX Settings: "Items older than N days (X items, Y MB) will be deleted now." Neither says "posted". `ContentRepo.olderThan` documents `postedAt`, so the developer followed the port.
- For stories `postedAt` is within 24 h of download, so no practical difference. For **posts** it differs after any backlog: phone off or no session for 10 days, N = 7, a post made 10 days ago and downloaded this morning is deleted at the next retention run (24 h job), possibly before the user ever opens it. Silent, irreversible, and the user's mental model ("kept N days") is broken.
- Characterised by `retention age basis (finding F1)` in `qa_t019_test.dart`.
- Fix without a port change: after `olderThan(cutoff)`, also require `max(detectedAt, latest downloadedAt) < cutoff` (or at least `detectedAt < cutoff`). The preview count in Settings (T-033) must use the same rule. Needs a Lead decision on the basis; document it in UX.

### F2 (major, liveness): skew guard rule 2 can block retention for everything
- One candidate with `detectedAt`/`downloadedAt` after `now` makes the whole run return `clockSkew`. A stale future-dated row (recorded during a bad forward clock jump) stays a candidate forever and blocks every other expired item until real time passes its timestamp, which can be months or years.
- Characterised: with a future item (+400 d) and a legitimate expired item, retention is skipped today and a day later.
- Fix: do not skip the run; exclude the future-dated candidates (and report a count in `RetentionResult`), delete the rest. The rest are judged by `postedAt` against `now`, so they are no less safe than before. Optionally repair the stale timestamps (not in scope).

### F3 (minor, acceptable): rule 3, 30-day idle disables retention
- All targets paused or no finished run for more than 30 days: retention is skipped until a run finishes (characterised). It fails safe (deletes nothing) and recovers on the next finished run. The spec defines no guard, so this is a proposal; acceptable. Note: any finished run counts, so a run with a bad clock refreshes the reference.

### F4 (minor): race between `listByTarget` and the target delete
- The use case lists the target's content once. Content added after that (a download finishing, a check run) is cascaded away when the target row is deleted, and its gallery file is orphaned (same end state as keep media, but unintended). Characterised in `RemoveTarget races`.
- Fix (cheap): loop `listByTarget` until it is empty (bounded) before `targets.delete`; and T-021 should pause the target (status or lock) during removal so no new downloads start. An in-flight download inserting a row for a deleted target would fail the FK; T-021 must handle that.

### F5 (minor, inherent limit): forward clock jump followed by a finished run
- If the clock jumps forward and a check run finishes before retention runs, rule 1 and 3 are satisfied with the wrong clock and everything older than the window is deleted (characterised, `LIMIT` test). Cannot be fixed from a wall clock alone. Mitigation idea: cap one pass to a bounded number or share of the library, or require the pass to be preceded by a UI confirmation if more than X% would go. Out of scope for T-019; note for T-021.

### F6 (minor): `GalleryPermissionDenied` blocks delete-media removal permanently
- If a file is not owned by Storize, `RemoveTarget(deleteMedia: true)` returns `targetRemoved: false` on every attempt. The UI (T-031) must explain this and offer "Remove, keep downloads". Also `GalleryStorageFull` on delete is not in the port's documented throws (only PermissionDenied/WriteFailed) but is handled the same as a failure (tested), so no harm.

### F7 (minor): thumbnails left behind
- Agree with the developer: `MediaCache` has no thumbnail delete, and thumbnails live in `files/thumbs` (support dir, not the OS-clearable cache), so they leak permanently. I agree with the proposed `Future<void> deleteThumbnail(int mediaFileId)` on `MediaCache`; also consider thumbnails in `cleanupOrphans`, since a crash can still leave some. It is a port change, so it needs Lead approval and its own task (adjust T-010 fake and real); it does not block T-019.

### Other checks (no issue)
- **Keep-media meaning (BR-6, UX S-10):** rows are gone and the files stay in the gallery; Storize cannot list or re-adopt them. A re-added target only downloads new items (watermark, FR-63) or stories still live, so duplicates are limited. The UI copy should say the files remain but leave the app.
- **Fake vs drift cascade:** `FakeTargetRepo.delete` calls the `FakeContentRepo` listener which removes content and media, matching T-005 FKs (`content.target_id` CASCADE, `media_file.content_id` CASCADE; asserted in `storize_data` `schema_structure_test.dart:240` and `content_repo_contract.dart:367`). `activity_event.target_id` is SET NULL and `check_run` has no target FK; the use cases touch neither, and the fake activity repo does not model the FK (not exercised here, covered by T-005 tests).
- **Crash points:** only `deleteByIds` mutates DB state, in chunks of 50 after the files of the chunk; a crash loses at most that chunk's rows and the re-run removes them.
- **Results leak:** `toString` of `DeleteContentResult`, `DeleteFailure`, `RemoveTargetResult`, `RetentionResult` show counts, IDs and exception codes only; QA test checks no URI, `content://`, file name, username or `Pictures`.
- **Result objects instead of `Unit`:** a harmless superset of the spec; agree. No activity events: fine, FR-52 lists no delete event.
- **Retention deletes pending (no file) old items too:** by design, characterised.
