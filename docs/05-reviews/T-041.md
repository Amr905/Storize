## Findings
- **F1 (Medium) Page-mode cursor drops same-second posts.** `PagePlans.postsScroll` keeps posts with `takenAt.isBefore(cursor.takenAt)` and the cursor is the last delivered post's second. Any tie that straddles a page boundary is lost for good. Reproduced: pageSize 2, posts at t=900, 500, 500, 100 gives page 1 = [p1, p2] and page 2 = [p4]; p3 is never delivered (test "posts sharing the cursor second are dropped (KNOWN)"). Likelihood: a carousel is one post, but bulk uploads and API-scheduled posts do share a second. A tie hits only when it falls on the 12-post boundary, so it is rare per page but real across a long history (roughly one page in a few hundred for normal accounts, high for bulk uploaders). It is silent, so a backfill ends "complete" but incomplete. Cheap fix: put the pks delivered at the boundary second in the cursor (`v1|t|igCursor|pk,pk`), keep posts with `takenAt <= t` and drop those pks; or cursor (time, pk) with a total order (time desc, pk desc). Direct mode is not affected (it uses Instagram's `end_cursor`; `takenAt` is only a fallback for a switch to page mode, where the same loss applies after a direct to page switch).
- **F2 (Low) Direct `fetchHighlightItems` double-prefixes a caller id that already starts with `highlight:`** (`highlight:highlight:x`), and the result is silently empty. Page mode rejects the same id (`bad_highlight_id`). Inconsistent; callers use `RemoteHighlight.id` (already stripped), so no live path. Fix: strip the prefix on input, or reject it in both modes.
- **F3 (Low) Cursor seconds overflow wraps silently** (`v1|9223372036854775807|x`): no crash, direct sends `x` as `after`, Instagram rejects it. Harmless; optionally bound the seconds in `PostCursor.parse`.
- **F4 (Info)** The direct `after`/`first` and highlight variables are unverified (spec v0.3); nothing here checks them against a real response. Needs a device test (DEVICE_TESTS.md was updated by the developer).
- **F5 (Info)** gitleaks not available in the workspace; CI must confirm.
