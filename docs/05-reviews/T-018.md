## Findings
- **F1 (Medium) adoption can take another item's file.** `_adopt` calls `findExisting(relativeDir, displayName)` for any item with a `.part`, and never checks whether another media row already owns that URI. With a display-name collision, B is marked DONE pointing at A's gallery file; deleting either removes the other's file (BR-9). Repro: skipped test "adoption must not take a gallery file owned by another item". Fix: the finder or `_adopt` must reject URIs already referenced by a different row; also compare size with the `.part`.
- **F2 (Medium) the re-entrancy guard is per object only.** Two `DownloadPending` instances (e.g. foreground + WorkManager) both open the same media id, append to the same `.part` and save twice (2 openMedia calls, duplicate gallery entry). Repro: skipped test "two DownloadPending instances ...". Fix: an inter-instance lock (claim row DOWNLOADING atomically, or the T-021 run lease). The Lead should decide if T-021 owns it; if so, record that in T-021's AC.
- **F3 (Low, by design) deadline is checked only between items.** A stalled stream is not cut at the deadline; the 8 of 10 minute budget is the only headroom. Suggest a per-stream timeout in T-021 or `openMedia`.
- **F4 (Info)** the finder (`GalleryFileFinder`) and thumbnails have no real port yet; the app must wire a finder, or the "after save, before row update" kill duplicates the gallery file.
