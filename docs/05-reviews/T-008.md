### Concurrency
- 30 interleaved save/load calls (1 ms backend latency) all return the old or the new blob and never throw or report.
- 20x (save, load, clear) in parallel: every load gives null or the blob. The final store state matches the backend (`containsKey == (load != null)`).
- 10 accounts saved in parallel do not bleed into each other.
- The class has no mutable state, and each backend operation is atomic per key. The real guarantee comes from the plugin (one `SharedPreferences` apply per write), which this layer cannot test.

### Contract parity with `FakeSessionStore`
Round trip, replace, idempotent clear, missing gives null: identical. Two divergences are pinned by tests:
1. The real store throws `ArgumentError` on `save` when `sessionid` / `ds_user_id` is missing or empty. The fake accepts anything.
2. A local-time `capturedAt` comes back as UTC from the real store. The fake returns it as given.

**Recommendation:** make the fake enforce the same required cookies on `save`. The rule is part of the vault's observable contract (TECH_SPEC §5.1), and a use-case test that saves a half-built blob should fail in the fake, not only on the phone. Moving `requiredCookies` into `storize_domain` or `storize_model` would let both use one constant. Do it as a small follow-up under Lead approval, because the fake is T-004's file. Divergence 2 is minor: either normalise to UTC in the fake or ignore it.

### Decision judgements
| Decision | Judgement | Reason |
|----------|-----------|--------|
| Default `AndroidOptions` (AES-GCM data key, RSA-OAEP key in the Keystore), no `encryptedSharedPreferences` | **OK** | Verified in `~/.pub-cache/.../flutter_secure_storage-11.2.0/CHANGELOG.md` (11.0.0: "Removed `encryptedSharedPreferences` parameter from `AndroidOptions`"). `android_options.dart` hard-codes `_keyCipherAlgorithm = AES_GCM_NoPadding` and `_storageCipherAlgorithm = AES_GCM_NoPadding`, and `defaultOptions = AndroidOptions()`. The 11.2.0 changelog says nothing about a different default |
| `resetOnError: true` (default) | **OK, with a T-034 requirement** | Verified: in `FlutterSecureStorage.java:~1044`, after a failed migration with `resetOnError`, it calls `deleteAllDataAndKeys`. That removes **all** plugin entries, so the T-034 PIN hash is lost together with the session. For T-034 the only recoverable result is "the user sets a new PIN": TECH_SPEC §5.2 stores the hash in the same storage, and the `appLock` flag lives in shared_preferences, so the two can disagree. **T-034 must treat "appLock = true but no PIN hash" as a reset state.** It must not unlock silently and must not lock the user out forever. It should clear the flag or force PIN re-creation, and tell the user. `resetOnError:false` would throw on every call and be worse. Add this to the T-034 task notes and the §5.2 spec. Note that the wipe also happens without any Dart-side error, so the vault's callback is only called for the read-error path |
| `load` validates the required cookies (`invalid_shape`) | **OK** | A blob without `sessionid` / `ds_user_id` is useless, and reporting it logs the account out early instead of failing on the first request |
| `save` / `clear` propagate platform errors | **OK** | A failed save must be visible to the login flow. Swallowing would show "logged in" with no stored session |
| Caught exceptions dropped, not wrapped | **OK** | Verified by the leak hunt: platform and format messages can quote the data, and dropping them is what keeps the tests clean. The cost is a less specific diagnosis, but the reason code is enough |
| `markLoggedOutOnUnreadable` swallows repo errors | **OK** | A missing account (deleted row) must not crash a background run. Tested. Minor: a swallowed DB failure leaves the status as `active`, and the next load will report again, so it self-heals |
