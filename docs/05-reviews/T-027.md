## Findings

### F4 (major, NFR-12): open time grows with the number of distinct days
Each day is a `SliverMainAxisGroup`, which lays out every group eagerly (the tiles inside stay lazy, so the developer's "fewer than 60 tiles" check cannot see this). The developer's perf data spans only about 24 days.
Measured by `qa_t027_perf_test.dart`, 5,000 items, ready list, JIT debug on this box (noisy, other agents running):

| items per day | days | open time |
|---------------|------|-----------|
| 25 | 200 | 248 ms |
| 5 | 1,000 | 791 ms |
| 2 | 2,500 | 2,210 ms |
| 1 | 5,000 | 7,322 ms |

A phone is slower than this box. Realistic heavy use (20 accounts, years of posts and no retention) can reach 1,000+ days, so the 1 s budget is at risk. Fix idea: one flat `SliverList` over rows (date header, account header, tile row) with sticky headers from a pinned-header package or a custom delegate, or paginate by day. The QA test pins `perDay == 1` as "above 1 s" and must be flipped when fixed.

### F5 (medium, measurement honesty): the stream replacement hides about 500 ms
The perf test replaces `allContentProvider` with `Stream.value(list)`. Through the real in-memory `FakeContentRepo.watchLibrary` (sort and join of 5,000 rows) the same screen opens in 740 ms against 248 ms (QA-PERF, same data shape). The drift query with the media join is not measured at all, and the developer's note "about 5x headroom" is not true once the repo is in the path. `watchLibrary(ContentFilter())` also loads all 5,000 rows with their media and re-groups on every emit (each download or viewed mark). Recommend T-037 measures the real drift path on a device, and consider a paged or limited query later.

### F1 (minor): Delete can be started again while a delete is in flight
The selection and the Delete button stay live while `DeleteContent` runs and no progress is shown. A second tap and confirm runs `DeleteContent` again for the same ids (`FINDING F1` test: the gallery sees the URI twice). T-019's re-run semantics make this harmless for data (the second pass sees "missing"), but it is wasted work and the user gets two snackbars. Fix: a `_deleting` flag that disables the action and shows progress. Rapid double tap on the dialog's Delete button deletes once (test passes).

### F2 (minor): partial failure clears the whole selection and the snackbar only states the failures
3 selected, 2 fail: "2 items couldn't be deleted", selection cleared, nothing says 1 was deleted. The kept items are not re-selected, so a retry means reselecting. Better: keep the failed ids selected and say "1 deleted, 2 couldn't be deleted". The count itself is accurate (failures from `DeleteContentResult`); a thrown `DeleteContent` reports all N as failed even if some went through.

### F3 (medium, delete safety): selection survives a kind switch or account filter
Selection mode keeps the Stories/Posts switch and account chips live. Select a story, switch to Posts: the bar still says "1 selected", no tile is selected on screen, and Delete removes the hidden story from the gallery after a confirmation that only says "Delete 1 item?". Same with an account chip (2 hidden items selected, 3 unselected tiles shown). It only deletes what the user selected, and only after confirming, but the user cannot see what. Fix: clear the selection when the kind, filters or data change (or hide the switch and chips in selection mode). Share silently drops hidden ids, so the two actions also disagree.
