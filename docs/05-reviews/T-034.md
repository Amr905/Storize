## Questions from the brief
1. **PinVault crypto.** PBKDF2-HMAC-SHA256, 210 000, 16-byte salt, 32-byte output: confirmed (vectors above). Versioned `v1:`. Malformed values (19 variants: `v2`, `V1`, iterations `0`, `-1`, `1.5`, 20-digit, `10^9`, `10 000 001`, bad base64 in salt and hash, extra or missing fields, empty, 1-byte hash, truncated base64, 16-byte prefix of the real hash, 33-byte hash with the real one as prefix, bad length key) never throw and never unlock; `10^9` is refused as `PinNotSet` in under 500 ms (cap is 10 000 000, see F-7). Wrong-length or non-digit PINs cannot be set.
2. **Cooldown.** Count written before compare (yes). Reset only on success (yes). Persisted (yes). Corrupt or unreadable attempts value starts a cooldown (yes). A far-future tampered deadline is clamped to 30 s (yes). Back-jump restarts at 30 s (yes). Forward-jump: see F-4. No escalation; the spec only says "30 s after 5 failures", so this matches. Small note: a kill between the 5th count and the cooldown write gives one extra guess (the 6th wrong PIN starts the cooldown); not observable by an attacker, negligible.
3. **Fail-open default.** See F-1. Wired=true with unwired providers is **fail-closed, no crash**: all providers unwired gives phase `failed` (locked, Retry); settings wired but PIN store unwired gives locked. Only a background event with `clockProvider` unwired throws (wrapped `UnimplementedError`), and the app stays locked.
4. **Gate coverage.** Every route is behind the redirect; nothing renders before the setting is read (`checking` counts as locked and `build` returns it synchronously, so the router's first redirect already sees locked); no loop; pushed pages dropped after re-lock; the lock screen shows only the logo, the title and digits (text inventory test, no `Image`, no `NavigationBar`, no `AppBar`).
5. **Lifecycle.** Covered under AC 4. `hidden`/`paused` ordering OK (`??=`). Not covered by design: recents thumbnail and the one-frame flash (F-8).
6. **Disable and enable.** Covered under AC 1 and 5. Biometric enabling is offered only when `isAvailable()` (strong type present) and requires a successful prompt first. Disable clears hash, length and attempts.
7. **Reset state.** Never silently unlocks (tested, including resume cycles). The trade-off is acceptable for a true secure-storage wipe, but the trigger is too broad: see F-3.
8. **Guardrails.** Clean (table above). Theme research: F-2.

## Findings
| ID | Severity | Finding |
|---|---|---|
| F-1 | **major** | **Fail-open default.** `appLockWiredProvider` defaults to `false`, and `main.dart` is a bare `runApp`. Nothing enforces the override: a composition root that forgets `appLockWiredProvider.overrideWithValue(true)` ships an app with the setting "on" and no lock. Repro: test `QA fail-open default ... KNOWN RISK` in `lock_qa_test.dart` (settings say enabled, flag not wired: `appLockedProvider == false`). **Recommend fail-closed by default**: default the flag to `true` and give the other screens' tests a `lockDisabledForTests` override (or a shared test harness), because the unwired path is already safe (`failed`, locked, Retry). If the Lead keeps the current design, the composition-root task must add the guard test I left skipped in `lock_wiring_guard_test.dart` (asserts `main.dart` references `appLockWiredProvider`, `pinStoreProvider`, `biometricAuthProvider`). |
| F-2 | **major** | **No AppCompat theme.** `local_auth_android` 2.3.0 README, "Android theme": the `LaunchTheme` parent must be a `Theme.AppCompat` theme "to prevent crashes on Android 8 and below". `app/android/app/src/main/res/values/styles.xml` and `values-night/styles.xml` use `@android:style/Theme.Light.NoTitleBar` / `Theme.Black.NoTitleBar`, and minSdk is 26, so **API 26 and 27 devices can crash when the biometric prompt opens**. CI cannot see this (build only, no device). On API 28+ the system prompt does not need it. Fix: change both `LaunchTheme` parents to `Theme.AppCompat.DayNight.NoActionBar` (appcompat arrives transitively through `androidx.biometric`), keep `NormalTheme`, and add the device check to the T-037 checklist (Android 8.x). Not verified on a device here. |
| F-3 | **major** | **Reset state is triggered by "unavailable", not only by "wiped".** `resetRequired = !hasPin && !biometricAvailable`. (a) A biometric-only lock has no PIN by design, so any moment the sensor reports unavailable (HW unavailable, lockout on some OEMs, face/camera busy, enrolment removed) shows "create a new PIN", and that unlocks. (b) `PinVault` converts a secure-storage **read exception** into `hasPin == false`, so one transient keystore error looks like a wipe, and then `setPin` **overwrites the real hash**. Repro (a): test `QA reset state ... KNOWN RISK` (biometric-only lock, `available=false`: new PIN accepted, `/library`). Fix: store a sentinel (for example `storize.lock.configured`) in secure storage when the lock is enabled; offer a new PIN only when the flag is on **and the sentinel is missing** (a real wipe takes the sentinel too). For "sentinel present but biometric unavailable" show "Fingerprint unavailable, try again" with Retry. Make `PinVault` return a distinct result for read errors instead of `PinNotSet`. |
| F-4 | minor | **Cooldown uses the wall clock.** Moving the device date forward 30 s ends the cooldown (test `KNOWN LIMITATION`). The attacker needs the Settings app, which means an unlocked phone, and each try still costs a PBKDF2 run (about 2.6 s here under JIT) plus UI taps. Without the clock trick, exhausting 4 digits takes about 1 h per 10^3 tries at 5 per 30 s. Recommend a monotonic source (`SystemClock.elapsedRealtime` from the plugin, with the boot-count to detect reboots) as a hardening task, not a blocker. A longer or escalating cooldown would cost more than it gains for this threat model; the spec says 30 s. |
| F-5 | minor | **`verify()` is not serialised.** 5 concurrent wrong guesses count as 1 (read-modify-write race). Test `parallel verify calls` is **skipped** with the reason, because the UI has a busy guard and nothing else calls it. A simple in-vault `Future` chain fixes it. |
| F-6 | minor | **`biometricOnly: true` still accepts class-2 (weak) biometrics.** `local_auth_android` 2.3.0 builds the prompt with `BIOMETRIC_WEAK or BIOMETRIC_STRONG`. `isAvailable()` only requires that a strong type exists, so on a phone with a strong fingerprint and a weak face unlock, the face can unlock Storize. The spec says "strong biometrics". Not fixable through `local_auth`; document it or accept. |
| F-7 | minor | **Iteration cap 10 000 000 is generous.** 210 000 took 2.6 s and 1 000 000 took 8.4 s in a JIT test run, so a tampered 10M would block one verify for minutes (inside an isolate, UI stays alive). Needs write access to secure storage, so low risk. Suggest cap 1 000 000 and floor 100 000 for `v1`. Also: 210k in pure Dart may be 1 to 3 s on a mid-range phone at unlock; measure on a device (T-037). |
| F-8 | minor (accepted by dev) | No `FLAG_SECURE` (recents thumbnail shows content); one-frame flash on resume before the lock redirect. Agree with the developer: follow-up, not T-034. |
| F-9 | info | `AppLockRow` is not mounted in `SettingsPage` yet (`grep AppLockRow lib` finds only its own file). Integration belongs to the settings screen task; make sure its AC includes it. |
| F-10 | info | `LocalAuthBiometric` had no tests; I added 3 (strong only, errors mean false, `biometricOnly: true` passed). |
