### 1. Seen-mutation blocking (UD-3), most important
Method: `qa_hook_harness.js` runs the real `hook.js`. Each scenario sends the mutation in one shape; "reached" = the name was present in the
URL, headers or body of what the fake network received.

Blocked (never reaches the network, a `blocked` notice is posted): string body; `URLSearchParams` body; `fetch(Request, {body})` (init body);
XHR string body; XHR with a `URL` object; beacon string and beacon `URLSearchParams`; the paths `/api/graphql`, `/api/graphql/`,
`/graphql/query`, a relative URL, `instagram.com`, `i.instagram.com`, `graph.instagram.com` (the match is on the name, not the path);
a missing, `null`, string or `undefined` config (falls back to the default list). A second injection does not wrap `fetch` twice.

**Reaches the network (bypass), all fail open:**
| Shape | Why |
|---|---|
| `fetch(new Request(url, {method:'POST', body}))` | `init` is undefined; the Request body is never read |
| `fetch(new URL(...), {body})` | `input.url` is undefined for a `URL` object, so `url` is null and the whole check is skipped |
| `FormData`, `Blob`, `Uint8Array` body (fetch), `FormData`/`Blob` (XHR), `Blob`/`FormData` (beacon) | `formOf` returns null for anything but string / `URLSearchParams` |
| JSON body | parsed as a query string, so the key is the whole JSON text |
| Name only in a header (`x-fb-friendly-name`) (fetch, XHR) | headers are not looked at |
| Name only in the URL query (POST) or a GET with the form in the query | the query is not looked at |

Real-world weight: the T-002 capture identified the real mutation by `fb_api_req_friendly_name` in a string body, so today's web client uses the
covered shape. But the hook is the ONLY barrier (native Android cannot see POST bodies), the protected effect is visible to the story owner
(BR-8) and cannot be undone, and Instagram ships the web app continuously. A fail-open barrier that depends on one serialisation is not
enough. Tested by `qa_t014_test.dart` ("BYPASSES": one pinned test that documents today's behaviour, and 14 `skip:` tests for the wanted one).

Other checks:
- **Iframe / worker context:** not testable off-device. The user script runs in each frame whose origin matches the allow-list, and nothing
  hooks a `Worker`, `SharedWorker` or service-worker context, or a realm taken from a fresh `about:blank` iframe (`iframe.contentWindow.fetch`
  is unhooked). Not seen in the capture; keep it on the device list and rely on the canary (QA-F3).
- **Request before the hook installs:** with `WebViewFeature.DOCUMENT_START_SCRIPT` the plugin uses `addDocumentStartJavaScript`, which is
  before page scripts. Without it (old WebView), I read the plugin (`UserContentController.generateCodeForDocumentStart`,
  `InAppWebViewClient.onPageStarted`): the script is injected by `evaluateJavascript` in `onPageStarted` and again at document end, a race
  with the page. `webview.dart` never checks the feature (QA-F5).
- **Can the page detect the fake 200?** Fetch: `Response` 200, `content-type: application/json`, `url` is `''`, no other header, body
  `{"data":{},"extensions":{"is_final":true},"status":"ok"}` (no `xdt_mark_story_reel_seen` field). XHR: readyState 4, status 200, `readystatechange`,
  `load`, `loadend` as plain `Event` (not `ProgressEvent`); `responseType` `arraybuffer`/`blob` gets a string (QA-F9). A page that validates the
  mutation payload, reads headers or retries could notice; unknowable off-device (device item).
- **Custom list that omits the seen mutation:** `PageHookConfig(blockedFriendlyNames: [])` and `['Other']` both reach the hook as given, and the
  mutation is sent (tests "an empty or foreign list REPLACES the default" and the Node scenario). **Recommendation: the seen mutation must
  always stay blocked.** Union the default in `PageHookConfig` (and in `hook.js`: `blockedNames = DEFAULTS ∪ cfg`); let the config only add names (QA-F2).

### 2. Secrets
- Logs: only operation names, counters, failure class and `runtimeType`. A hostile reply (keys and values containing the fake sessionid, csrf,
  dtsg), a throwing driver (message holds a fake cookie) and a throwing clear: none of the fake secrets, the `doc_id` or the username appears in
  the extractor log, the governor log, the failure, `PageDiscovery.toString()` or `PageSessionConfig.toString()`. `HookEvent`, `HookCapture`,
  `HookBlocked` and the DOM types print no payload.
- Tokens and `doc_id` stay in memory: no file in `lib/page` writes a file, uses `SharedPreferences`, `print` or `debugPrint`;
  `PageDiscovery` expires them (6 h / 30 min) and hands out a copy. A bad `doc_id` shape and bad token keys are dropped on parse.
- Debug inspector (`app/lib/debug/inspector_screen.dart`): its prelude is `{handler, includeBody:false}`. `includeRequestSecrets` is never on
  there (tested), the URL carries no query, and the blocked list falls back to the default, so the inspector blocks the seen mutation too (Q1 agreed).
  `PageHookConfig.prelude()` is the only place that turns on `includeBody` and `includeRequestSecrets`, and it only reaches the headless view.
- gitleaks `dir` and `git`: no leaks (table above).

### 3. Origin checks (AC6)
Frame origins that must be dropped, all dropped: `https://instagram.com.evil`, `.evil.test`, `www.instagram.com.evil.test`, two punycode
look-alikes, `https://www.instagram.com@evil.test`, `evil.test/https://www.instagram.com`, ports `:444` and `:0`, a trailing dot, upper-case
host and scheme, `http://`, `about:blank`, `null`, empty, `data:`, `blob:https://www.instagram.com/...`, `file://`, trailing slash or path, leading/trailing space,
NUL and newline, and `help.`/`l.`/`i.instagram.com`. Claimed origins (frame fine): the same list subset, plus non-string types (null, int, bool, list, map).
`https://instagram.com` and `https://www.instagram.com` are accepted (also mixed: frame `instagram.com`, claim `www`). A `blocked` notice needs both
origins. Message URLs with userinfo, look-alikes, `http`, `wss`, `blob`, protocol-relative and relative are dropped (a host in upper case
is accepted because `Uri` lower-cases it; harmless).
**Important nuance (QA-F4):** the developer calls the frame origin "native". On Android it is not: the plugin's bridge JS computes
`window.location.origin` inside the frame and sends it with the call (`JavaScriptBridgeJS`: `origin = window.location.origin`;
`JavaScriptBridgeInterface` just passes it on). It is honest per frame (a subframe cannot make the bridge lie without the per-WebView bridge
secret), so the check works for the cases above, but it is not independent of the page. `webview.dart` sets neither
`javaScriptHandlersOriginAllowList` nor `javaScriptHandlersForMainFrameOnly`, which enforce the same rule on the native side.

### 4. Governor discipline
- One governed `pageLoad` per load; a 3-user `fetchStories` is three runs; the third waits for a refill (cost 3, burst 6). Four different
  operations started at once with `Future.wait` give 4 sessions, `maxActive == 1`, 4 `cost=pageLoad` and no `cost=api`, each session cleared
  and disposed (serialised by the governor).
- `open()` throwing: `UnknownFailure('webview_unavailable')`, no timer armed, no clear (nothing opened), log without the exception text,
  the lease is released (the next call runs).
- **`open()` that never completes (QA-F6):** the governed call never returns, no timer exists (the 20 s timer is armed after `open`), and after
  10 min of fake time the future is still pending. In the real adapter `await created.future` and `view.run()` have no timeout, and `clearData` and
  `dispose` in the `finally` are awaited with no timeout either. One stuck WebView holds the account's governor lease and blocks every call.
- `load()` after a throw, timeout, failure or throwing clear always disposes; `dispose` is called once per session.

### 5. Parsing and failures
- Unrelated captures (50 of them, a no-name one) never answer a plan; a failure inside an unrelated capture does not end the run.
- Two matching captures: the first that answers wins. A matching failure first (`please wait`) then a good body: the failure wins (rate limit
  pauses the account; correct, fail-safe).
- A capture without a friendly name never answers a plan.
- A capture after the timeout fired is ignored (listener checks `done`) and not recorded in the discovery.
- **Empty reel list first, real one second: "no stories" wins (QA-F8).** If the page fires the reel query twice (tray, then the user), an empty first
  answer means a missed 24 h story. Unknown off-device.
- Failure classes are the T-013 classifier (login/challenge/suspended/disabled redirects, 401/404/429/5xx, `please wait`, checkpoint, feedback,
  not authorized); a load error is `NetworkFailure`.

### 6. Global cookie jar vs the login WebView (S-02) (QA-F7)
`InAppPageDriver` calls `CookieManager.deleteAllCookies()`, `WebStorageManager.deleteAllData()` and `InAppWebViewController.clearAllCache()`
before it sets the session cookies, after the run and when `open` fails. These are app-wide. S-02 is not written yet (T-026), so there is no
conflict today, but a page-mode run while the login WebView is open (a foreground retry; or the background isolate, which is a different Dart
isolate, so **a Dart mutex does not protect it**) would delete the user's login cookies mid-login and the login would appear to fail for no reason.
**Recommendation:** an app-wide `WebViewLease` held by S-02 for its whole lifetime and checked by the page driver with `tryAcquire`, not waiting:
`UnknownFailure('webview_busy')` and no wipe. It must work across isolates (a row like `governor_lease`, or a lock file in the app's private dir),
with a TTL so a crash does not lock page mode forever. S-02 should also clear the jar itself after it has read the session. Put the lease port in
`storize_domain` (Lead approval, port change) or inside `storize_instagram` and pass it from T-015/T-026. Related, Info: every run starts with empty web
storage, so Instagram sees a fresh browser (new `mid`/`ig_did`) with an old session each time; keep the device cookies in `SessionBlob` if S-02 captures them.

### Opinion on the developer's open questions
1. **Inspector blocks the seen mutation by default:** agree, and keep it non-overridable (QA-F2). I verified the inspector prelude omits the list (so the default applies) and never sets `includeRequestSecrets`.
2. **Username from the shared `UsernameCache`:** acceptable, but see QA-F12: the cache must be persistent or seeded from the targets, or page mode fails exactly when it is needed (after a restart).
3. **Story cost 3 per user:** correct under ADR-9 (a page load is heavy). Document the throughput (QA-F13) and use `latest_reel_media` to avoid loads.
4. **No page-mode `verifySession`:** agree for MVP. Every load already maps login/challenge redirects to `SessionInvalid`, so `latestStoryTime`/`resolveUser` work as a session probe if T-020 needs one in page mode.
5. **Global cookie jar vs login WebView:** real, see QA-F7 and section 6 (cross-isolate lease).
6. **Renamed accounts:** `refreshUser` and the profile paths compare ids and return `TargetNotFound`; the story path does not (QA-F11). Fix the story path and let RunCheck refresh the username.
7. **No ADR needed:** I disagree. UD-3 (block the seen mutation, "always blocked", fail-closed without document-start) and the shared WebView lease are decisions of ADR-0003 / ADR-0009 scale. An addendum to ADR-0003 is enough.
8. **Full melos run about 3 minutes:** it was about 3 min here too (instagram 47 s, app 74 s, data 52 s). Fine; run packages in parallel in CI later.

### 2. F1 adversarial, new shapes (`qa2_*`)
Blocked, never reach the network, `blocked` notice posted: name split across stream chunks (init-body stream to `/api/graphql` is blocked as

legacy `/stories/reel/seen` (any case, also as beacon URL) and `xdt_mark_story_reel_seen` in a body; `sendBeacon` with `URLSearchParams`,
`Blob` (read async, still returns `true`), typed array and `URL` object; reused XHR (blocked twice; ok then blocked; abort after an async body);
a page that wraps the hooked `fetch`, calls it via `call` / `apply` / `Reflect.apply`, re-injects the hook (flag set or cleared),
subclasses `XMLHttpRequest`, or takes `Object.getOwnPropertyDescriptor(XHR.prototype,'send')`; keepalive with string, `Request`, `Blob` and stream;

`javaScriptHandlersForMainFrameOnly` does not stop the request itself. It stays device test 11 and the canary is the net.

**Residual (pass today, pinned as `RESIDUAL` tests, none exploitable by a server that decodes once):**
- Triple percent-encoding of every character (the decoder runs two passes).
- JSON body with `\uXXXX` escapes (the web API takes a urlencoded form; plain JSON IS blocked).
- A `ReadableStream` as `init.body` to a **non-GraphQL** instagram path, and a nameless request that carries only `doc_id` (the block is by
  name by design, ADR-0003; Dart's canary also checks the reply key `xdt_mark_story_reel_seen`, which catches the nameless case).
- Look-alike unicode (full-width, dotted I, long s, combining mark) is not matched, and does not need to be: the server does not fold it.
  Case folding of the real name works.

**No needed query is blocked.** Reel, profile, posts, timeline and media-info names, each as string, `FormData`, `Request`, XHR and typed array

URL and even a username `seen_mutation`: not blocked (the needles are the full names). **One deliberate over-block:** `init.body` as a

### 3. F3 breaker scope: recommendation
`SeenGuard.shared` is a Dart `static`, so it is per isolate: the foreground UI isolate and the workmanager isolate each have their own, and it
resets on every process start. **Not sufficient for production.** A trip means the block failed on this WebView/Instagram version; the next
background run (new isolate) would load stories again and mark them seen again, once per run, until someone notices.
**Recommendation: T-015 persists it** (a row in the settings table or a `shared_preferences` key, read before each story load, written on
trip, cleared only by an explicit user/Lead action, with the trip time and app/WebView version for diagnosis) and surfaces it as a health
state in the UI. Keep `SeenGuard` as the in-memory mirror. Not a T-014 blocker because the canary and the in-isolate breaker work and the port
cannot be persisted without T-015's storage.
