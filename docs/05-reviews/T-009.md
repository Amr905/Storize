## Decision judgements

1. **ApplicationExitInfo instead of WorkInfo.stopReason: OK as an interim, conditional.** It avoids a work-runtime dependency and the data is useful for the battery diagnosis (LOW_MEMORY, USER_REQUESTED, EXCESSIVE_RESOURCE_USAGE). But it reports process deaths, not per-worker stop reasons, and starts at API 30, not 31. Condition: the Lead amends AC5 in TASKS.md and tells T-021/T-037 that per-work stop reasons must come from elsewhere if needed (for example logging `workmanager` results). The Dart doc already says `workName` is always `process`.
2. **Test deps proposed, not added: OK to defer, but AC6 stays open.** Approve the three test deps (junit 4.13.2, androidx.test ext junit 1.2.1, runner 1.6.2) and add `testInstrumentationRunner` before T-009 can be marked fully done. Without them the 99+67-line Kotlin tests are unverified code. Nothing runs them in CI.
3. **Video fallback to `Movies/Storize/<dir>/`: OK, and needed.** Android 10 MediaProvider rejects `Pictures/` for the video collection with IllegalArgumentException (caught, then retried). The returned `relativePath` reports the folder used. Condition: T-010 must store and use the returned relativePath, and the user's gallery will show videos under a Movies/Storize album, which deviates from spec §3 (document it there). Confirm in P-4.
4. **`openBatterySettings` returns a string outcome: OK.** Dart decodes it into an enum with a strict parser (unknown strings are badResponse, tested).
5. **OEM component names best-effort: OK.** Each is resolve-checked and falls back to app details. Not testable without those phones. P-4 will tell which work.
6. **API <= 28 URI is `content://` from the scan, or `file://` after 5 s: OK.** `managedUri` accepts both, and file paths are canonicalised and confined to `Pictures/Storize`. Caller must treat the URI as opaque (state this in T-010).

## Kotlin review notes

- **IS_PENDING flow:** insert(pending=1) then copy then update(pending=0). Failure paths: exception during copy, null OutputStream (explicit IOException), disk full (IOException/ENOSPC mapped to STORAGE_FULL), `update < 1`, all land in `catch (Exception)` which deletes the row and rethrows. Streams use `use {}`, no leaked cursors (`query(...)?.use`, fd `.use`). Gap: `Exception`, not `Throwable` (F6).
- **Collisions:** MediaStore silently renames to `name (1).jpg` on 29+; `FileNames.unique` does the same on the legacy path. The returned map has `uri`, `size`, `relativePath` but not the final display name (F4). `relativePath` is accurate.
- **Threading:** all media calls and lastStopReasons run on one single-thread executor. `runCatching` catches Throwable, then `mainHandler.post { deliver }` calls success/error exactly once. Rejected execution or null executor answers error once. `mainThread` calls run on the platform thread. Executor `shutdown()` in `onDetachedFromEngine`. Queued tasks still finish and post to a dead engine; harmless.
- **Thumbnails:** retriever released in `finally`, bitmaps recycled, size clamp 16..4096.

### New finding

**F9 (medium, security hardening): `delete` accepts a MediaStore collection URI, bypassing the row check.**
`managedUri` accepts any `content://media/...` URI, with no check that it names a single row. For example, `content://media/external/images/media` (no `/<id>`):
1. `guard.classify(uri)` queries the whole collection and reads `RELATIVE_PATH` of the first visible row (`moveToFirst`, no ordering).
2. If that one row is a Storize row, the result is `ALLOWED`.
3. `resolver.delete(uri, null, null)` then runs against the collection with no selection, which deletes every row the app can write: all Storize rows on API 29+ without permission, and on API 29+ with `READ_MEDIA_IMAGES`/legacy write access, or on API <= 28, the user's other photos as well.

Repro (needs a device; not reproducible on the JVM): insert one file, then call `delete('content://media/external/images/media')` (or `.../file`, `.../video/media`). Also worth testing: URIs with `?` or a trailing path that provider matching treats as the collection.
Suggested fix: in `managedUri` (or `classify`) require the last path segment to be a numeric id (`ContentUris.parseId` succeeds) and the path to be `/external/<images|video|file>/media/<id>` or `/external/file/<id>`; add a pure-Kotlin check so a JVM test can pin it; and reject a non-empty query string. Consider also re-checking `RELATIVE_PATH` through a `delete` selection (`WHERE _id=? AND relative_path LIKE 'Pictures/Storize/%'`) to close the check-then-delete race.
Not fixed by this task's tests: it is Kotlin product code, so I only report it.

Other residual notes (low, no action required for T-009):
- Time-of-check/time-of-use between `classify` and the following `delete`/`openFileDescriptor` (single user, low risk; the selection-based delete above would remove it).
- No Kotlin test exercises `StorizeGuard` or `MediaStoreOps` (need Android); `insert` rollback, `classify` by SDK level and F9 depend on instrumentation (P-4).
- `file://` + `delete` on API 29+ deletes via `File.delete` inside a Storize root; fine because the path is canonicalised and confined.

### Answers

1. **Can any URI still reach a whole collection or a non-Storize row?** No, by code review.
   - `managedUri` now requires `UriPolicy.mediaItemId(raw) != null` for every `content:` URI, and `delete`, `exists` and `size` all pass through `managedUri`. `videoThumbnail(uri)` checks it directly. `mediaItemId` is a whole-string check on the raw input: prefix `content://media/` (lower-case, exact), no `?` or `#`, exactly four segments `<volume>/(images|video)/media/<id>`, volume `[A-Za-z0-9_-]+` (no dots, `%`, spaces), id `[1-9][0-9]*` that fits a Long. Collection URIs, `/file/` URIs, `..` segments, trailing slash, extra segments, userinfo authorities and other schemes all return null. The `delete` path uses `requireNotNull(mediaItemId(uriString))` on the same string it parsed, so there is no parser mismatch.
   - `delete` runs one statement, `_id = ? AND (path in Storize range)`, against the item URI. Even if a URI got through, the selection scopes it to one id inside a Storize folder. The follow-up `classify` only picks `false` or `PERMISSION_DENIED`; it never deletes.
   - `file://` URIs are unchanged: confined by `guard.fileAllowed` (canonical, sibling-safe).
   - `exists` and `size` still do check-then-open (`classify` then `openFileDescriptor`): a TOCTOU is possible but read-only and harmless.
2. **Range-bound prefix.** Correct. For `lo = "Pictures/Storize/"` and `hi = "Pictures/Storize0"` (`/` is 0x2F, `0` is 0x30), only strings starting with `Pictures/Storize/` satisfy `lo <= s < hi`. I checked: `Pictures/StorizeX/`, `Pictures/Storize0`, `Pictures/Storize0/a/`, `Pictures/Storize.x/`, `Pictures/Storize-/a/`, `pictures/storize/a/` and `PICTURES/STORIZE/a/` are all outside; `Pictures/Storize/` and children are inside. Values are bound arguments, no `LIKE`, no `%`, no functions; the clause is parenthesised so the `OR` cannot escape the `_id` condition. The JVM tests pin the SQL text, argument order, no-LIKE, and the range for `StorizeX`, `Storize2`, no trailing slash and `DCIM`. Prefixes must end in `/` (enforced by `require`, tested).
   - Caveats (low): (a) case: the range is BINARY. If MediaProvider declares the column `COLLATE NOCASE`, an upper-case path would match; harmless because Android's emulated storage is case-insensitive too, but not verified on a device. No JVM test pins the upper-case result. (b) The delete range accepts a row whose path is exactly `Pictures/Storize/` (no user folder), while `relativePathAllowed` (used by `classify`) requires 3 segments, so there are two slightly different definitions of "ours". Both are inside Storize, so no confinement impact.
3. **`DATA` on API <= 28.** `dataPrefixes` uses `root.absolutePath` + `/`. This matches how the plugin itself writes: `insert` builds files under `guard.legacyRoot()` (`getExternalStoragePublicDirectory`, e.g. `/storage/emulated/0/Pictures/Storize`) and scans `file.absolutePath`, so MediaStore stores the same absolute form. A consequence of not canonicalising: if a row's `DATA` is stored in another alias (for example `/sdcard/...`), the delete affects 0 rows, then `classify` (canonical `dataPathAllowed`) says `ALLOWED`, and `delete` returns `false` silently instead of deleting. That fails safe (nothing outside Storize is deleted) but is a functional edge; and a `DATA` containing `..` that was written by another app would pass the string range. Only a malicious app with storage write on API <= 28 could create such a row; treat as informational. Needs an API 28 device/emulator run (P-4) to confirm.
4. **Do the JVM tests pin it?** Yes for the pure parts: item URI accept list (`external`, `external_primary`, SD volume id, large id), reject lists (collections, 0, -1, `05`, `+5`, trailing space, overflow, Arabic-Indic digit, query, fragment, `files`/`file`/`audio`/`thumbnails`, extra segment, trailing slash, `..`, wrong authority/scheme/case), selection SQL and args, range membership, and bad input. Instrumentation tests were added for collection URIs, query/fragment URIs and deleting a foreign row (`PERMISSION_DENIED`, row intact); they compile in CI but run only in P-4. Not covered: upper-case range check; behaviour of the real provider on `NOCASE`.
