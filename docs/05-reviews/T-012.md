### Budget simulation (fake time, 24 h, seeded Random, one isolate, one account)
- Demand: stories at :00/:30 (3 calls) and posts every 3 h at :15 (50 sequential calls) = 8 post rounds.
- Result: **544 calls = 22.7/h** (ADR estimate 23/h). **Max in any rolling 60 min = 56** (never above 60).
- **A 50-call post round takes 48-49 min** (6 burst calls in about 25 s, then 1 per minute; the story runs compete for the same tokens). So the round is throttled, not a burst of 50. The 3 h period leaves about 2 h 10 min idle, so no carry-over backlog.
- Saturation (constant demand, 6 h): 367 calls, **max in any 60 min = 65** = 60 refill + 6 burst. Under *continuous demand* the "60 per hour" ceiling is 66 in a window, not 60 (the burst is spent on top of refill). Normal scheduling never reaches it (56 max). Not a defect, but the ADR wording "60/h" is really "60/h + burst 6"; consider burst 3-4 if 60 is ever to be a hard window cap.

### Starvation (item 4)
- A queues 50 calls; B calls `run`: **B gets `GovernorBusy` after exactly 2 min** while A had finished 8 of 50. The lease is released only when A's queue is empty, so B can wait about 44 min (a 50-call post round) and gets `GovernorBusy` every time during it.
- Impact for the UI: a manual "Check now" while the background worker runs a post round fails for up to about 45 min with `GovernorBusy`. Since both share one token bucket the user would wait anyway, but "Busy" is a worse message than "Checking…" (S-07). It is not an Instagram-safety issue. When A is only in a short token wait (one queued call) B gets in right after (STARVATION 2: no error).
- Recommendation (QA-F4): release the lease between calls when waiting more than a few seconds, or let UI-priority calls jump the queue; at minimum make the adapter map `GovernorBusy` to a "worker is busy, queued" state rather than an error, and have T-017 call UI checks in the same isolate/governor where possible.

### API usability (T-015 / T-017)
- `GovernorPaused.toFailure()` -> `RateLimited(retryAfter)` verified. `canAfford(calls:)` and `remainingTokens` verified (6 api calls fit, 7 do not; 2 page loads fit, 3 do not).
- **Double-report is easy to misuse (QA-F6):** feeding a failure back after the governor already handled it (for example mapping `GovernorPaused.toFailure()` to `Err(RateLimited)` and passing it to `reportRateLimited`, or wrapping an outer `run` around an inner one) escalates the multiplier to x4 although only one rate limit happened (test "feeding GovernorPaused back ...": mult=4.0). Pause length is not extended (longer wins), but the x4 for 2 h is.

## Findings
| ID | Severity | Where | Description / fix |
|---|---|---|---|
| QA-F1 | Medium | `request_governor.dart` `reportRateLimited` -> `_exclusive`/`_acquire` (about l.119-125, 262-270) | A rate limit reported from another isolate is **dropped** with `GovernorBusy` if the lease is held more than `acquireTimeout`. Same in `_finish` after a lease takeover (masks the original error with `GovernorBusy` and loses the limit). A rate limit is the most important signal. Fix: in `reportRateLimited` and `_finish` never time out (use a longer/unbounded acquire) or write the back-off with a lease-less compare-and-set repo method; at least swallow `GovernorBusy` in `_finish` and rethrow the original error. |
| QA-F2 | Medium | `_jitterWait` (about l.378), `_prepare` loop; lease expiry in the repo | Clock moved **backwards** (phone time change/timezone fix-up, sync): `lastRefillAt` and a released lease's `expiresAt` are in the future, so the next call waits as long as the jump (1 h -> 1 h 0 m 3 s; 1 day -> `GovernorBusy` for the other isolate, blocked a day). No negative waits, no huge refills (good), but a stuck governor. Fix: if `bucket.lastRefillAt` is after `now`, treat it as `now` (clamp the jitter reference and refill base); `acquire` in the repo must treat `expiresAt > now + ttl` as expired and `release` should set `expiresAt` to the epoch, not `now`. Needs T-005's DAO to do the same. Two tests are `skip`ped until fixed (the skip reasons name this finding). |
| QA-F3 | Low-Medium | `_withBackoff` (about l.393) | `retryAfter` is uncapped: 30 days gives a 720 h pause. A bad header/parse bug could disable the app for a month silently. Fix: cap the pause (suggest 24 h, config `maxPause`) and log it. |
| QA-F4 | Low-Medium | `_exclusive` (about l.210-225) | The lease is held for the whole queue, so a UI check is refused with `GovernorBusy` for up to about 45 min during a post round (see Starvation). Fix as above. |
| QA-F5 | Low | `run` | Re-entrant `run` for the same account deadlocks silently. Document it in the dartdoc and ensure the extractors (T-013/T-014) do not nest (for example a page-mode fallback must be called after the direct `run` returns, not inside it). Optional guard with a Zone value. |
| QA-F6 | Low | `reportRateLimited`/`run` API | Double report escalates x4. Safer API: make `reportRateLimited` private/`@visibleForTesting`, or add a `bool alreadyHandled`-style guard by having `run` return/throw a `GovernorRateLimited` marker that adapters pass through unchanged, and have `GovernorPaused.toFailure()` carry a flag so that a repeat report of a paused account is ignored (a limit received while *paused by the governor itself* should not count as a repeat). |
| QA-F7 | Info | ADR-9 wording | Max calls in any 60-min window under constant demand is 66 (burst + refill), 56 in the realistic day. |

## Adversarial probes (item 1)
- **Concurrency with the per-call lease** (3 governors, one yielding fake repo that awaits around every acquire/read/write, mixed api and pageLoad calls of 700 ms): `maxInFlight == 1`; 72 calls, 108 tokens spent in 1 h 42 min (budget 6 + 102 = 108, within the bound); max calls in any 60 min window 45; the smallest gap from any call end to the next start is exactly 1.5 s (= `jitterMin`). No overlap, no overspending.
- **Read-modify-write under the lease**: every `writeBucket` goes through `acquire` first in the same iteration; the repo refuses a write from a non-holder. Probe: 3 isolates x 4 calls (no jitter) from a full bucket need exactly 6 min (12 tokens - 6 burst), measured to within 1 ms; a lost update would shorten it. I also checked every persisted write: `lastRefillAt` never goes back and tokens never exceed `min(6, previous + refill)`.
- **Jitter fairness abuse**: two hot isolates, 30 calls each: elapsed >= 54 min, max calls in 60 min <= 66. The `jitterMin` owed to a peer only shortens the random gap, it never bypasses the bucket, so the combined rate is bounded by the bucket (60/h plus the 6 burst). Fairness cannot raise the combined rate.
- **Windows**: x2 holds until pause-end + 2 h (-1 s: 2, +1 s: 1). A repeat 23 h after the pause end gives x4, which also decays 2 h after the second pause end. A limit 25 h after the end gives a fresh x2.
- **Costs**: page load costs 3 (6 -> 3 -> 0, the third waits exactly 3 min), burst caps at 6 after 3 idle days.
- **`GovernorBusy` on a true timeout**: still thrown.
