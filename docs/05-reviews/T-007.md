### Findings
- **F-1 (Medium, bug in product code)**: `packages/storize_data/lib/settings/shared_prefs_settings_repo.dart:281-283` (`_instant`). The guard `raw.abs() > _maxEpochMs` does not catch `int.minValue` (-9223372036854775808), because `abs()` overflows to a negative number. `DateTime.fromMillisecondsSinceEpoch` then throws `RangeError`, so `get()`, `update()` and `watch()` throw on a corrupted store. This breaks the "reads never throw" contract.
  - Reproduce: `prefs.setInt('storize.riskAcknowledgedAt', -9223372036854775808); await repo.get();`
  - Failing test: `QA corruption negative and huge timestamps never throw`.
  - Fix: `if (raw is! int || raw < -_maxEpochMs || raw > _maxEpochMs) return null;`
- **F-2 (Low, decision needed)**: A small negative timestamp (e.g. -1) is accepted as a valid 1969 instant instead of falling back to null. The request said a negative timestamp should fall back. Pre-1970 values are never legitimately written. Either clamp to `< 0 -> null` or accept the behaviour as is. The QA test accepts both.
- **F-3 (Info)**: The developer's flagged risk, no batch write. A crash mid-update can leave only some of the changed keys written. Severity is **Low**. Each key is an independent, individually valid value, and `_decode` re-validates every field on read. Every possible partial state is therefore a valid `AppSettings`. Only the unit of atomicity is lost, for example a story interval saved without its matching wifiOnly change. No settings have cross-field invariants, and `_write` only touches changed keys, which keeps the window small. No action needed. Revisit if a cross-field rule is added.
- **F-4 (Info)**: The queue runs reads and writes one at a time, so there are no lost updates. The cost is that `watch` emits in queue order, not synchronously like the fake. This does not affect parity of the event sequence.
